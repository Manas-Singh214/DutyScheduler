PROJECT DOCUMENT
Exam Duty Allocator

This document explains the Exam Duty Allocator as it is implemented in this repository. It is intended for project handover, maintenance, demonstrations, and technical interviews. It describes the current code rather than proposed features. The application is designed for local use. The Windows launcher starts the user interface and API on the same computer.

1. Project overview

Exam Duty Allocator is a web application for preparing examination invigilation schedules. A user enters an institution, an exam, exam sessions, teachers, and rooms. The backend assigns teachers to rooms for each session while considering saved duty totals from earlier exams. The user reviews the schedule, can make acceptable assignment exchanges, downloads a compact Word duty chart, and can explicitly save completed duties to the account history.

The application also supports importing teacher and room lists from CSV or Excel files, importing prior teacher duty totals from Excel, viewing and exporting saved history, and listing teachers who remain available as standby staff in each session.

The application is composed of two local development processes:

- A React frontend served by Vite at http://localhost:5173.
- A FastAPI backend served by Uvicorn at http://localhost:8000.

The frontend calls the backend over HTTP. The local default database is SQLite. Docker Compose provides an alternate self-hosted setup using PostgreSQL.

2. Main requirements addressed

- Generate a room-by-room duty chart showing room, shift one teacher, and shift two teacher.
- Keep one teacher from being assigned to more than one room in the same session.
- Use prior duty totals to give priority to teachers with fewer historical and current duties.
- Randomize ties so equal-duty teachers do not always receive assignments in the same order.
- Show standby teachers by session and allow eligible standby replacements.
- Allow exchanges between assigned teachers when the exchange does not increase the total duty-count spread.
- Import teacher and room lists from CSV and Excel files.
- Maintain teacher totals and completed exam records in account-scoped history.
- Import and export historical totals as Excel workbooks.
- Export a compact DOCX duty chart with standby lists rather than a fairness matrix.
- Run locally from one Windows batch file without manually launching backend and frontend commands.

4. Repository structure

backend/app/main.py
Defines the FastAPI application, HTTP routes for allocation, upload, export, health checks, and optional serving of the built frontend. It includes the authentication router, configures CORS, initializes database tables, and runs the legacy username migration. The static directory is backend/static when running from the repository and /app/static inside the Docker image.

backend/app/allocator.py
Contains the duty assignment algorithm. It cleans and de-duplicates teacher and room names, validates scheduling inputs, assigns teachers using history-aware greedy selection, randomizes equal-total choices, and calculates standby and duty-count results.

backend/app/models.py
Defines Pydantic data models for sessions, allocation requests, assignments, schedules, duty counts, allocation responses, and DOCX export requests.

backend/app/auth.py
Defines SQLAlchemy account and history models, username and password registration and sign-in, JWT creation and verification, legacy username migration, exam history operations, and Excel history import and export.

backend/app/database.py
Creates the SQLAlchemy engine and session factory. Without DATABASE_URL it creates a SQLite database at data/exam_duty.db in the project root. It creates the data directory when needed.

backend/app/exporter.py
Creates the compact server-generated DOCX document. The chart contains the room number and two teacher shift columns, then standby lists. The fairness matrix is not rendered as a separate table.

backend/app/rate_limit.py
Creates the SlowAPI limiter. The default storage is in-memory.

backend/tests/
Contains Python unittest tests for allocation, export and spreadsheet import, account behavior, historical balancing, and legacy username migration.

frontend/src/App.jsx
Owns the primary frontend state and workflow. It handles sign-in, registration, API calls, history access, allocation requests, schedule export, and marking an exam complete.

frontend/src/components/DataEntryForm.jsx
Collects school and exam details, sessions, teachers, and rooms. It accepts pasted text and spreadsheet imports.

frontend/src/components/Dashboard.jsx
Displays the room duty chart, shift pairs, standby staff, schedule exchanges, standby substitutions, history completion, and DOCX export actions.

frontend/src/utils/spreadsheetImport.js
Parses CSV in the browser and sends Excel list files to the backend for first-sheet parsing.

frontend/src/utils/docxExporter.js
Provides a client-side DOCX fallback if server-side DOCX export fails.

frontend/src/utils/api.js
Selects the API base URL. During Vite development the default backend address is http://localhost:8000. In a production build the default is the same origin.

EXAMSCHEDULER.bat
Checks for Python and npm, creates the backend virtual environment if missing, installs Python requirements, installs frontend dependencies if Vite is missing, starts both services in separate command windows, and opens the browser.

Dockerfile
Builds the frontend using Node.js, installs the Python backend requirements, copies the built UI into the backend static directory, and runs the API server.

docker-compose.yml
Runs the application and PostgreSQL with persistent database volume storage. It expects local environment variables in a .env file.

5. Data model and important types

Scheduling request types

SessionInput
- id: optional string.
- date: string.
- time_slot: string.
- session_name: optional string.

Dates and time ranges are represented as strings, not Python date or datetime objects. The UI sends the selected values as text. The backend currently does not parse or validate their calendar or time semantics.

AllocationRequest
- school_name: string.
- exam_name: string.
- sessions: list of SessionInput.
- teachers: list of strings.
- rooms: list of strings.
- history_totals: dictionary mapping teacher-name strings to integer duty totals.

Assignment
- room: string.
- teacher: string.

SessionSchedule
- session_id: string.
- date: string.
- time_slot: string.
- session_name: string.
- assignments: list of Assignment.

TeacherDutyCount
- teacher: string.
- total_duties: integer.

AllocationResponse
- school_name and exam_name: strings.
- schedule: list of SessionSchedule.
- fairness_matrix: list of TeacherDutyCount objects used by the application for totals and persistence.
- total_teachers, total_rooms, and total_shifts: integers.
- standby_teachers: list of teacher-name strings not used in any generated session.
- history_totals: dictionary of historical totals used for allocation.

The fairness_matrix remains part of the in-memory/API result because the dashboard uses it to show teacher totals and save the exam. Its presence does not mean it is printed in the DOCX. The exporter creates the compact duty chart and standby text.

Database entities

School
- Integer primary key.
- Name string.
- Represents the history workspace for an account.

User
- Integer primary key.
- Foreign key to School.
- Unique username string, normalized to lowercase.
- Password hash string.
- Role string.
- A legacy email field and verified field remain for compatibility with older database layouts. New registration does not require an email address.
- New accounts receive a synthetic value in the legacy email column ending in @accounts.invalid so the old non-null unique column remains satisfied. It is not a real address, is not sent mail, and is not part of the sign-in form.

DutyHistory
- Integer primary key.
- School foreign key.
- Teacher name string.
- Integer total duties.
- A uniqueness constraint prevents duplicate teacher names within the same school workspace.

CompletedExam
- Integer primary key.
- School foreign key.
- Exam identifier string, exam name string, and completion timestamp.
- The combination of school and exam identifier is unique.

ExamDuty
- Integer primary key.
- School foreign key.
- Exam identifier, teacher name, and integer duty count.
- Stores the per-exam contributions that make up the history.

DutyImport
- Integer primary key.
- School foreign key.
- SHA-256 content hash of an imported workbook.
- Prevents importing the exact same workbook bytes into the same workspace more than once.

6. End-to-end user workflow

Starting the project

1. The user double-clicks EXAMSCHEDULER.bat in the repository folder.
2. The launcher checks whether Python and npm are available on PATH.
3. If backend/venv does not exist, the launcher creates a Python virtual environment there.
4. It installs or verifies Python packages from backend/requirements.txt.
5. If frontend/node_modules does not contain Vite, it runs npm ci in frontend.
6. It starts Uvicorn on the loopback address 127.0.0.1 port 8000.
7. It starts Vite on the loopback address 127.0.0.1 port 5173.
8. It opens http://localhost:5173 in the default browser.
9. The two terminal windows must remain open while the app is in use. Closing them stops the services.

Account creation and sign-in

1. A first-time user chooses account creation.
2. The username must be 3 to 32 characters and use letters, digits, dots, underscores, or hyphens. Usernames are converted to lowercase.
3. New account passwords must be at least 12 characters.
4. The backend hashes the password before storing it. It does not store the submitted password in plaintext.
5. The backend issues a signed access JWT that expires after 12 hours.
6. The frontend stores that token in browser localStorage and sends it as a Bearer token for protected API calls.
7. On later visits, the frontend checks the token with the account endpoint. Invalid or expired tokens are removed and the user is returned to sign-in.
8. There is no password reset, email confirmation, or account recovery. A forgotten account requires making a new account; the previous history remains in the old account.

Creating a schedule

1. The user enters institution name and exam name.
2. The user configures one or more sessions with date, time, and session label.
3. Teacher and room names can be pasted as comma-separated or newline-separated values.
4. CSV list files are read by the browser. Excel list files are sent to the backend, which reads the first worksheet and returns its rows. The frontend detects a likely teacher or room column from its header and lets the user select a column.
5. The frontend sends the request as JSON to POST /allocate and adds the Bearer token.
6. The backend loads history totals for the account's school workspace and replaces the request history_totals with those saved totals.
7. The allocator produces one assignment per room per session.
8. The frontend displays sessions in a room-based chart and shows standby teachers for each session.

Reviewing and changing a schedule

1. The user chooses an assignment in the chart.
2. The user can choose another visible assignment to exchange teachers, or choose an eligible standby teacher for that selected session.
3. The frontend recomputes total duties using saved historical totals plus the proposed schedule.
4. The change is accepted only if the maximum-minus-minimum duty count does not increase compared with the current schedule.
5. The UI updates the chart and the per-teacher duty counts after an accepted change.
6. Schedule edits are held in frontend state until the user marks the exam complete. They are not saved as completed history automatically.

Exporting and saving history

- Export DOCX sends the reviewed schedule to POST /export. The server returns a Word document. The frontend also has a browser-side DOCX fallback.
- The DOCX groups sessions into shift pairs and contains the room number, shift one teacher, shift two teacher, and standby lists. It does not display a fairness matrix.
- Mark exam complete sends teacher duty counts to POST /auth/history/record.
- The backend rejects a duplicate exam identifier within the same account workspace.
- History view shows saved teacher totals. An Excel history import adds totals to existing values.
- Re-importing exactly identical workbook bytes is rejected using the stored SHA-256 hash.
- History export downloads an Excel workbook with a Teacher Totals sheet and an Exam Log sheet.

7. Allocation algorithm

The scheduler is a greedy history-aware algorithm. It does not search every possible schedule or solve a general optimization problem.

For each request:

1. Teacher names and room names are trimmed and exact duplicate strings are removed while preserving first-seen order.
2. Empty teacher names and room names are rejected. At least one session is required.
3. Historical totals for teachers not in the current teacher list are ignored. Negative history values are treated as zero.
4. A current duty counter starts at zero for each listed teacher.
5. For each session, the allocator starts with all teachers marked available.
6. For each room in order, it finds the available teacher with the smallest historical total plus current-request duty count.
7. If multiple available teachers have the same minimum, Python SystemRandom selects one of them.
8. The chosen teacher is removed from the available set for that session, preventing two assignments in one session.
9. The chosen teacher's current duty total is incremented. Later sessions therefore account for assignments earlier in the same generated schedule.
10. Teachers never assigned in any session are returned in standby_teachers.

If a session has more rooms than listed teachers, allocation fails with a validation error. A teacher can be assigned once per session and may work again in a later session.

The algorithm makes a local fair choice at each room assignment. It is effective for balancing repeated duties when all assignments have equal weight, but it does not model teacher preferences, qualifications, absences, workload limits, room-specific constraints, or unequal duty weights.

The fairness rule depends on exact teacher-name matching. For example, "Asha Patel" and "asha patel" are different names in the history map. Users should use consistent teacher names across exams and imports.

8. API overview

Health and frontend

GET /health
Returns a simple status response used to verify that the backend is running.

GET /
Returns the built frontend index when backend/static/index.html exists in the repository layout. In local Vite development the UI is served by Vite instead.

Authentication and account

POST /auth/register
Creates a username and password account. Registration is limited to 5 requests per hour per client address.

POST /auth/login
Checks credentials and returns a signed access token. Login attempts are limited to 10 per minute per client address.

GET /auth/me
Returns details for the account associated with the Bearer token.

GET /auth/history
Returns the account workspace's teacher totals.

POST /auth/history/record
Records a completed exam and its teacher duty counts. Requires authentication.

POST /auth/history/import
Imports an XLSX or XLSM history workbook. Requires authentication, accepts up to 10 MB, and is limited to 5 requests per hour.

GET /auth/history/export.xlsx
Returns the account history as an Excel workbook. Requires authentication.

Scheduling and files

POST /allocate
Accepts an allocation request and returns the generated schedule. Requires authentication.

POST /import-list
Accepts an XLSX or XLSM workbook up to 10 MB and returns non-empty rows from its first worksheet. It is used for selecting teacher or room columns.

POST /export
Accepts a reviewed schedule and returns a DOCX file.

FastAPI provides interactive API documentation during local operation at http://localhost:8000/docs.

9. File formats and validation

Teacher and room list input

- Pasted input accepts comma or newline separators.
- CSV input is parsed in the browser, including quoted commas and escaped quote characters.
- Excel list input accepts .xlsx and .xlsm. The backend reads the active first worksheet using openpyxl.
- The list-file endpoint limits file size to 10 MB.
- CSV values are treated as text. The UI can choose a detected column, but does not enforce a fixed CSV schema.

History workbooks

- History import only accepts .xlsx and .xlsm.
- The first worksheet must have a recognized teacher-name heading and a recognized total-duty heading.
- Accepted teacher headings include Teacher, Teacher Name, Staff, and Staff Name.
- Accepted count headings include Total Duties, Duties, Duty Count, and Total Shifts.
- Counts must be non-negative integers.
- Imported values are added to current totals, not used as a replacement.
- Exact workbook bytes are hashed with SHA-256 to prevent accidental re-import of the same file.

DOCX output

- Word output uses python-docx on the backend.
- Browser fallback output uses the docx JavaScript package.
- Both output room and shift assignments and standby names.
- These two export implementations are separate and should be kept visually and semantically aligned when changed.

10. Configuration and local data

EXAMSCHEDULER.bat local development

The one-click launcher does not require a .env file. With no DATABASE_URL set, the backend uses SQLite at data/exam_duty.db. The launcher requires Python 3 and Node.js with npm available on PATH. First setup normally needs network access to install packages.

The app is bound to 127.0.0.1 by the launcher, so it is intended for the same computer rather than remote users on a network. The Vite development server uses port 5173 and the API uses port 8000.

Relevant environment variables

DATABASE_URL
Optional database connection string. If omitted, local SQLite is used. Docker Compose sets this to a PostgreSQL connection string for its database service.

APP_SECRET_KEY
Secret used to sign JWT tokens. Development has a fallback key for ease of use. Production mode rejects the known development key.

APP_ENV
When set to production, authentication startup requires a non-default APP_SECRET_KEY and a PostgreSQL DATABASE_URL.

CORS_ORIGINS
Comma-separated list of allowed browser origins. The local default allows localhost and 127.0.0.1 on port 5173. CORS must allow the Authorization request header because the frontend sends the Bearer token to restore a saved session and access protected endpoints. If this header is blocked, the browser prevents the session check and the frontend returns to sign-in.

RATE_LIMIT_STORAGE_URI
SlowAPI storage configuration. Defaults to memory://. In-memory rate limits do not coordinate across multiple application processes.

VITE_API_URL
Optional frontend build-time API base URL. In Vite development the default is http://localhost:8000; in a production build the default is same-origin.

Docker Compose configuration

The Docker Compose setup is separate from EXAMSCHEDULER.bat. It expects a .env file with APP_SECRET_KEY and POSTGRES_PASSWORD, and can use APP_PORT and RATE_LIMIT_STORAGE_URI. It starts PostgreSQL with a persistent Docker volume and starts the application in production mode. Because the backend production guard requires PostgreSQL, the standalone SQLite development mode and production Docker mode have different database requirements.

11. Security and privacy behavior

- Passwords are hashed with the recommended pwdlib password hasher and Argon2 support.
- Authentication tokens are JWTs signed with HS256 and expire after 12 hours.
- The frontend stores the access token in localStorage. This is convenient but means browser-accessible JavaScript can access it.
- Account, history, and allocation endpoints require a Bearer token where marked.
- The local launcher binds services to loopback addresses. It is not a public website or cloud deployment.
- Username and password recovery are not implemented.
- Rate limiting uses client IP address and in-memory storage by default.
- The project is not configured as a multi-instance or high-availability deployment.
- The development secret must not be reused for a production deployment.
- Database backups are not automatically created by the application.

12. Tests and how to run them

Backend tests use Python unittest and are in backend/tests.

The tests cover:

- Preference for teachers with lower historical totals.
- Cumulative balancing across repeated exam runs.
- Randomized equal-duty tie choices and assignments for a large staff list.
- No duplicate teacher in a room assignment set for a session.
- User creation, normalized usernames, sign-in, duplicate names, and rejected credentials.
- History separation between distinct accounts.
- Recording an exam and importing the same history workbook only once.
- Migration of old email accounts to usable unique usernames.
- Excel first-sheet parsing.
- DOCX room/shift columns and standby list without a fairness audit matrix.

To run tests from a terminal:

1. Open a terminal in the backend directory.
2. Activate the backend virtual environment or use its Python executable directly.
3. Run python -m unittest discover -s tests.

The frontend has an npm build and lint script in frontend/package.json. The build verifies that Vite can compile the UI. There is no dedicated frontend automated test suite listed in the current package scripts.

13. Important limitations and trade-offs

- The one-click launcher is Windows-specific. Linux and macOS users must start the backend and frontend using their platform's shell commands or use Docker.
- The launcher needs local Python and Node.js installations. On first run it also needs package download access.
- The local database belongs to the machine and project folder. Moving the repository without copying data/exam_duty.db does not move local account history.
- A local SQLite database is appropriate for a single local process and modest use. Concurrent multi-user deployments should use a managed or self-hosted PostgreSQL database with backups.
- The batch file runs the development servers with reload enabled. It is not a Windows service installer and is not intended as a hardened production deployment.
- The current local configuration runs frontend and backend on separate ports. A built frontend served by FastAPI is supported in the Docker image.
- The fairness algorithm has no constraints for teacher availability, qualifications, maximum workload, or preferences.
- History depends on exact teacher names. Inconsistent spelling or capitalization can split one real teacher into multiple totals.
- Workbooks are limited to 10 MB. The list importer reads the first worksheet; history import also reads the first worksheet.
- The history importer adds totals. It does not overwrite or reconcile totals with an external source.
- Account history is tied to a username. If a user forgets the credentials, there is no built-in recovery or migration from the old account.
- Rate-limit storage is in-memory unless configured otherwise; it is intended for one app process.
- The backend requirements use minimum version ranges rather than exact pins. Recreating the environment later may install newer compatible package versions.
- The API's session dates and time slots are strings. Formal date parsing, time-zone treatment, and overlap detection are not currently implemented.
- The scheduler's random tie breaking means the same input can produce different equally fair schedules. This is intentional.

14. Difficult engineering problems and design decisions

Fairness across multiple exams

Random selection on its own can repeatedly assign the same teachers. The allocator uses saved historical totals as the primary selection value, then adds duties already assigned during the current generation run. Randomness is only used to select among equal minimum totals. The application stores history only after the user explicitly confirms that an exam has been completed, preventing a generated but unused draft from affecting future exams.

Keeping one teacher per session

The same teacher should not be assigned to two rooms in a single time slot. The allocator maintains an assigned-in-session set and removes selected teachers from that session's candidates. This allows a teacher to work in another session while preventing simultaneous duplicate room assignments.

Allowing schedule edits without undoing fairness

Manual swaps can undermine a balanced generated schedule. The dashboard recalculates totals after a proposed change and compares the spread between the highest and lowest cumulative totals. It rejects a change if that spread becomes larger. This is a simple guardrail; it is not a complete optimization of all possible schedules.

Supporting both CSV and Excel

CSV can be handled directly in the browser without uploading it. Excel parsing uses openpyxl on the API because browser support for workbook parsing is not part of the current stack. Both paths are normalized into rows, then the user chooses the column to apply.

Preventing duplicate history imports and exam logs

History imports add to existing totals, so importing the same file twice would inflate totals. The backend hashes workbook bytes and stores the hash per school workspace. Completed exams use a unique workspace and exam identifier constraint to reject duplicate completion records.

Operating without hosted services

The development launcher uses loopback addresses and a local SQLite database. It avoids cloud URLs and external database credentials. The trade-off is that history is stored on that computer and other computers cannot use the app unless a separate private hosting setup is configured.

15. Interview questions and suggested answers

Question: What problem does this project solve?

Answer: It reduces manual work when creating exam invigilation plans. It maps teachers to rooms for each exam session, provides a standby list, and uses earlier duty totals to help distribute repeated assignments fairly.

Question: Describe the architecture.

Answer: The frontend is a React application served by Vite in local development. It sends JSON and file-upload requests to a FastAPI backend. The backend validates schemas with Pydantic, runs allocation logic, and stores accounts and history through SQLAlchemy. SQLite is used by the local launcher. The app can also be built into a single service with Docker, using PostgreSQL in Docker Compose.

Question: Walk through a schedule generation request.

Answer: The user enters teachers, rooms, and sessions. The frontend sends an AllocationRequest to POST /allocate with a Bearer token. The backend loads the account's history totals, runs generate_allocation, and returns an AllocationResponse. The frontend displays the room chart and standby lists.

Question: How does the algorithm promote fairness?

Answer: For each room, it assigns the available teacher with the lowest sum of saved historical duties and duties assigned earlier in the current generation request. If several teachers tie, it chooses randomly using SystemRandom. A teacher assigned to a room is removed from that session's candidate set.

Question: Is this a globally optimal scheduler?

Answer: No. It is a greedy heuristic that makes a fair local choice at each assignment. It does not search all schedules or model preferences, qualifications, absences, or weighted assignments. A future version could use constraint programming or an integer optimization model if those constraints become necessary.

Question: Why randomize ties?

Answer: Equal historical totals represent equally eligible candidates. Random tie breaking avoids always favoring the first name in the input list while preserving the same minimum-total fairness rule.

Question: How are duplicate assignments within a session prevented?

Answer: The allocator tracks assigned teachers for the current session and removes each chosen teacher from that session's candidate list. It also rejects a session when there are fewer teachers than rooms.

Question: What happens if the number of rooms exceeds the number of teachers?

Answer: Allocation raises a ValueError that the API converts into an HTTP 400 response. The frontend displays the returned error.

Question: How does the application keep fairness after a manual swap?

Answer: The dashboard counts current assignments, adds stored history totals, and computes the max-minus-min spread. It permits a swap only when the proposed spread does not exceed the existing spread.

Question: Why is exam history saved only after review?

Answer: A generated schedule may be only a draft. Saving automatically would incorrectly affect future allocations if the schedule was never used. The user must explicitly mark the exam complete.

Question: What does the database store?

Answer: It stores users and password hashes, school workspaces, cumulative teacher totals, completed exam records, per-exam duty contributions, and hashes of imported workbooks.

Question: How are passwords handled?

Answer: Passwords are hashed with pwdlib using its recommended password hashing configuration, which includes Argon2 support. Login verifies the supplied password against the stored hash. The raw password is not stored.

Question: How does authentication work?

Answer: Successful registration or login returns a signed HS256 JWT with a 12-hour expiration. The React app stores it in localStorage and sends it in an Authorization Bearer header on protected calls.

Question: What is a JWT and why is it used here?

Answer: A JSON Web Token is a signed token containing claims such as a user identifier and expiration time. The API can verify its signature and expiry without creating a server-side session record for every request. The signing key must be secret and stable.

Question: What are the security limitations of this authentication design?

Answer: The token is kept in localStorage, which is accessible to JavaScript running in the page. The project has no recovery flow, uses an in-memory rate limiter by default, and requires a proper secret outside development. A hardened public deployment would need a security review, secure transport, backups, shared rate-limit storage, and careful browser threat mitigation.

Question: Why use Pydantic?

Answer: Pydantic validates and converts JSON request data into typed Python models. It provides clear schema definitions for sessions, assignments, and allocation requests, and FastAPI uses these schemas for API documentation.

Question: Why use SQLAlchemy?

Answer: SQLAlchemy provides a consistent ORM and database engine interface. It allows the app to use SQLite locally and PostgreSQL under Docker Compose while keeping account and history operations expressed as Python queries.

Question: Why use SQLite locally and PostgreSQL in Docker?

Answer: SQLite makes one-computer setup easy because it requires no database server. PostgreSQL is used by the container-based production-style configuration because it supports a dedicated database service and persistent volume. SQLite is not intended for scaling concurrent users.

Question: How are spreadsheet uploads protected?

Answer: The upload endpoints accept specific Excel extensions and reject files above 10 MB. The history importer validates required headers, integer duty totals, non-negative values, and duplicate workbook hashes. File parsing errors are returned as HTTP errors.

Question: How is a repeated history workbook detected?

Answer: The backend calculates a SHA-256 hash over the uploaded bytes and stores it for the account workspace. A later upload with the same bytes is rejected.

Question: Why use both server-side and client-side DOCX export?

Answer: The backend exporter is the primary path and uses python-docx. A browser implementation using the docx JavaScript package is available as a fallback if the server export request fails. Both paths must be maintained to keep output consistent.

Question: How does the project support local-only operation?

Answer: The Windows launcher binds the development servers to 127.0.0.1, uses a local SQLite file by default, and opens a localhost URL. It does not require a public URL or cloud database for ordinary local development.

Question: What does Docker add?

Answer: Docker builds the React frontend into static files, installs the backend, and lets FastAPI serve the built frontend. Docker Compose additionally starts PostgreSQL with a persistent volume. It offers a self-hosting route, but it is separate from the one-click Windows development launcher.

Question: What is CORS and why is it configured?

Answer: Cross-Origin Resource Sharing is a browser security mechanism for requests between different origins. In local development the frontend is on port 5173 and the API is on port 8000, so the backend permits the configured local frontend origins.

Question: How would you test the allocator?

Answer: Unit tests should cover lower-history preference, one assignment per teacher per session, the room-to-teacher capacity error, standby counts, randomized ties, and cumulative fairness over repeated exam runs. The repository has tests for these main cases.

Question: What does the current test suite not prove?

Answer: Unit tests do not prove that every browser interaction works, that the app is secure under hostile network conditions, or that every possible schedule is globally optimal. The current repository has backend unit tests but no dedicated frontend test suite.

Question: What happens if a teacher's name changes between imports?

Answer: The system treats it as a different exact name and maintains a separate total. Stable spelling and capitalization are necessary. A future improvement could add canonical teacher IDs or an alias/merge interface.

Question: What would you improve next?

Answer: Potential improvements include formal date/time validation, availability and qualification constraints, teacher IDs to avoid name mismatches, frontend automated tests, database backup and restore procedures, exact dependency lock for Python, configurable secure token handling, persistent shared rate-limit storage, and stronger production deployment hardening.

Question: Why is the backend environment not exactly reproducible?

Answer: The Python requirements specify minimum versions rather than exact pins and do not currently use a Python lockfile. The frontend does use package-lock.json with npm ci. Exact Python pins and a tested runtime matrix would improve reproducibility.

17. Summary

Exam Duty Allocator is a local-first full-stack application. React and Vite provide the browser interface. FastAPI and Pydantic expose validated API operations. A greedy randomized tie-break scheduler uses saved duty totals to balance assignments across sessions and exams. SQLAlchemy stores account-scoped history in SQLite for local use and PostgreSQL for Docker Compose. Excel and CSV imports feed the scheduler, and the application generates compact DOCX schedules with standby lists. The one-click Windows batch file automates the normal local development startup.

The central engineering trade-off is simplicity versus constraint completeness. The project prioritizes an easy local workflow and transparent duty balancing. It does not yet solve every real-world scheduling constraint or provide cloud-scale account sharing, automatic backups, or account recovery.

Python is a suitable choice here because:

- The scheduler algorithm can be expressed clearly using lists, dictionaries, sets, and loops.
- FastAPI and Pydantic make HTTP APIs and input validation direct to implement.
- SQLAlchemy provides database access without writing every query as handwritten SQL.
- python-docx creates Word files from Python objects.
- openpyxl reads and writes Excel workbooks.
- Python unittest is included in the standard Python installation for the backend tests.

Python 3 is a runtime requirement, not a feature that users need to understand to operate the app. The user double-clicks the batch file, and the batch file calls Python to start the backend. Python must still be installed on the machine. The current launcher checks that a command named python exists; it does not install Python or enforce a particular patch version.

The Dockerfile uses Python 3.11 for the container build. The local launcher uses the Python installation found on the computer. Use a currently supported Python 3 release with the required packages. The repository's backend requirements use minimum version declarations, so package compatibility should be checked if using a future Python release.

Python source files use the .py extension. The API package is backend/app. The main module is app.main, which is why the server command is uvicorn app.main:app when the working directory is backend.

22. What a .bat file is and what this launcher does

A .bat file is a Windows batch script. It contains Windows command-prompt commands that are executed in order. EXAMSCHEDULER.bat is a convenience launcher; it is not a separate compiled application and it does not contain the scheduler algorithm.

The user only needs to double-click EXAMSCHEDULER.bat in the project folder. The following is the execution sequence. Exact durations depend on the computer and internet connection.

Phase 1: Find the project folders

The command %~dp0 expands to the directory where EXAMSCHEDULER.bat is stored. This makes the launcher work when the project folder is moved, including when its path contains spaces. The script builds absolute paths to backend and frontend from that root.

Phase 2: Check required tools

where.exe python checks whether the Python command is available on PATH. where.exe npm.cmd checks whether npm is installed and available. If either command is missing, the script explains the missing prerequisite, pauses so the message can be read, and exits without starting the app.

The launcher does not install Python or Node.js. Install these runtimes separately if the checks fail. Restarting the terminal or Windows may be necessary after changing PATH.

Phase 3: Prepare Python's isolated environment

If backend/venv/Scripts/python.exe does not exist, the launcher runs python -m venv backend/venv. This creates a virtual environment for this project's Python packages. The environment keeps project dependencies separate from globally installed Python packages and other projects.

The script then runs the virtual environment's Python with pip install -r backend/requirements.txt. pip is Python's package installer. The requirements file tells pip which packages the backend needs. Version entries use greater-than-or-equal constraints, so pip installs a version that satisfies each minimum.

This command is run every time the batch file is started. pip checks whether installed packages satisfy the requirements and normally does not reinstall already satisfactory packages. If packages are absent or outdated relative to their declared minimums, pip may contact the Python package index and install them.

Phase 4: Prepare JavaScript dependencies

If Vite is not present in frontend/node_modules, the launcher changes into the frontend directory and calls npm ci. npm ci removes and recreates the dependency installation from package-lock.json. It can require internet access on the first setup.

Phase 5: Start the backend window

The start command opens a separate command window with the backend directory as its working directory. It runs the Python executable inside backend/venv and starts Uvicorn with app.main:app. The --reload option watches backend source files and restarts the development server after code changes. The --host 127.0.0.1 setting keeps this development server on the local computer. The API listens on port 8000.

The colon in app.main:app separates the Python module from the FastAPI variable. app.main means load backend/app/main.py. The final app means use the FastAPI object named app inside that module.

Phase 6: Start the frontend window

The second start command opens another command window with the frontend directory as its working directory. It runs npm run dev -- --host 127.0.0.1. The first -- starts an npm script; the second -- passes the remaining option to Vite. Vite listens on port 5173.

The /k option tells the Windows command processor to keep that frontend window open after starting the command. The backend window is also retained by the start process. Keeping these windows visible lets the user read startup errors and request logs.

Phase 7: Open the browser

The launcher waits two seconds and asks Windows to open http://localhost:5173 in the default browser. Startup speed can vary. If the browser opens before Vite is ready, wait a few seconds and refresh.

To stop the local application, close the backend and frontend command windows. The browser tab itself does not run the backend. Keeping the terminal windows open is necessary while using the app.

24. What Python does when the backend starts

Uvicorn imports app.main:app. Importing main imports the API models, scheduler, exporter, authentication router, database objects, and limiter.

The database module reads DATABASE_URL. If it is unset, it creates the data folder and constructs a SQLite URL pointing to the project-root data/exam_duty.db file.

The FastAPI module creates its application object, creates tables from the declared SQLAlchemy models, performs the legacy username migration, includes the account router, configures the rate limiter, and sets CORS rules.

The legacy migration checks whether the user table has a username column. For old email-based rows that do not have a username, it derives a lower-case username from the email's local part, resolves conflicts with a legacy suffix, and adds a unique index.

Uvicorn then listens for HTTP requests. A successful GET /health response indicates that the API process is running. It does not by itself prove every database operation, browser feature, or document download works.

In local Vite development, FastAPI normally serves API responses only. The React UI comes from Vite. In a Docker build, the Dockerfile copies frontend/dist into /app/static, and FastAPI can serve that static site from its root route.

25. What happens inside the frontend

The browser receives frontend/index.html from Vite. The HTML contains a div with the id root and loads frontend/src/main.jsx.

main.jsx imports React, ReactDOM, App.jsx, and the project stylesheet. ReactDOM creates the React root at the HTML element and renders App.

App.jsx decides what to display based on state:

- If the token is still being checked, it shows a loading state.
- If there is no valid account, it shows sign-in or registration.
- If the user has not selected another area, it shows the home screen.
- If the user starts a new schedule, it shows DataEntryForm.
- If a schedule exists, it shows Dashboard.
- If the user opens history, it shows the saved totals and import/export controls.

DataEntryForm keeps inputs in React state. On submit it normalizes the text into arrays and calls the callback supplied by App.

App serializes schedule inputs with JSON.stringify and uses fetch to send HTTP requests. For files, it uses FormData so the browser can send multipart form data. The access token is added to protected requests in the Authorization header.

Dashboard receives schedule data as props. It creates a table from sessions and rooms. React keys identify rows and buttons. On a swap it calculates a new schedule and calls the update callback, which replaces App's schedule state.

The browser's localStorage survives browser refreshes, unlike ordinary React state. The app uses it for the access token. It does not use localStorage to save the generated schedule or duty history.

26. What happens during one API request

Example: generating an allocation

1. The user presses the generate button.
2. DataEntryForm prevents the browser's default page submission and creates a JavaScript object containing school name, exam name, sessions, teachers, and rooms.
3. App receives the object and sets its loading state.
4. App converts the object to JSON text and calls fetch for POST /allocate.
5. The browser includes the local API address and the Authorization Bearer token.
6. The browser may send a CORS preflight request because the frontend and backend use different ports.
7. FastAPI routes the request to allocate_duties and validates JSON against AllocationRequest.
8. FastAPI's dependency mechanism resolves the current user from the JWT and opens a database session.
9. The route loads that user's history totals. Client-submitted history totals are replaced by the database values.
10. generate_allocation validates the teacher, room, and session inputs and selects assignments.
11. FastAPI serializes the AllocationResponse model to JSON and sends it with a success status.
12. The frontend parses the JSON, clears the loading state, stores the allocation in React state, and displays Dashboard.

HTTP status codes used by the API include:

- 200 for successful requests.
- 201 when a new account is created.
- 400 for invalid data or unsupported workbook contents in relevant routes.
- 401 when credentials or an access token are invalid or missing.
- 409 for duplicate usernames, completed exam IDs, or imported workbook hashes.
- 413 when a workbook exceeds the upload size limit.
- 422 when request validation fails.
- 500 when an unexpected server error occurs in routes that convert exceptions to HTTP responses.

The frontend checks response.ok. For non-success responses it tries to display the detail or message from the JSON response.

28. Why Docker is present and what its files do

Docker packages an application and its runtime dependencies into an image. Running an image creates a container, which is an isolated process with its own filesystem view and network configuration. Docker helps make the application environment more consistent between computers. It does not automatically make a service public on the internet.

The Dockerfile is a list of image build instructions. This project's Dockerfile uses two build stages.

Frontend build stage

1. Start from a Node 22 Alpine Linux image.
2. Copy frontend/package.json and package-lock.json into the build directory.
3. Run npm ci to install the frontend packages.
4. Copy the remaining frontend source.
5. Run npm run build to create frontend/dist.

Backend runtime stage

1. Start from a Python 3.11 slim image.
2. Set /app as the working directory.
3. Copy backend/requirements.txt and install backend packages with pip.
4. Copy backend/app into /app/app.
5. Copy the frontend build output into /app/static.
6. Set the default application port to 8000.
7. Start Uvicorn listening on 0.0.0.0 inside the container.

The container listens on all of its own network interfaces so Docker can connect to it. This is different from EXAMSCHEDULER.bat, which binds to the host computer's loopback address.

29. What docker-compose.yml and YAML are for

YAML is a human-readable text format for structured configuration. It uses indentation to show which values belong under which key. It is not the programming language that implements the scheduler.

docker-compose.yml is read by Docker Compose. It describes which containers to build or run and how they connect. The project declares two services.

db service

- Uses the postgres:16-alpine image.
- Reads the database username, password, and database name from configuration.
- Uses a named volume called exam-duty-data to keep database files when the container is stopped or recreated.
- Runs pg_isready as a health check so Compose can determine when PostgreSQL is ready.

app service

- Builds the app image using the root Dockerfile.
- Publishes the container's port 8000 through a host port, which defaults to 8000.
- Passes APP_ENV, APP_SECRET_KEY, DATABASE_URL, RATE_LIMIT_STORAGE_URI, and PORT to the backend.
- Waits for the database health check before starting.
- Uses a restart policy and an HTTP health check.

The database host in DATABASE_URL is db. Docker Compose places services on a private network where the service name resolves to the other container. The host application must not use db as its database host when running outside Docker.

The volume is what makes the database survive ordinary container removal. A named volume is separate from the app image. Deleting the volume deletes the persistent database contents, so volume cleanup must be deliberate.

The .env.example file is a template only. To use Docker Compose, create a file named .env beside docker-compose.yml and replace the sample APP_SECRET_KEY and POSTGRES_PASSWORD values. Do not share or commit a real .env file. The repository .gitignore excludes .env.

Docker Compose is optional. The everyday Windows path is to double-click EXAMSCHEDULER.bat. The batch launcher does not invoke Docker Compose and does not require Docker Desktop.

- Backend: 127.0.0.1 on port 8000.

32. Development workflow: how to change the project safely

Changing scheduler behavior

1. Update or add a Pydantic input or output type in backend/app/models.py if the API data shape changes.
2. Implement the algorithm change in backend/app/allocator.py.
3. Keep the endpoint in backend/app/main.py focused on validation, history loading, calling the allocator, and translating errors.
4. Add or update tests in backend/tests/test_allocator.py.
5. Run the backend tests from the backend folder.
6. Check that Dashboard still understands the response properties.

Changing an API route

1. Define request and response schemas in backend/app/models.py or backend/app/auth.py for authentication-related data.
2. Implement route behavior in backend/app/main.py or the account router in backend/app/auth.py.
3. Add authentication dependencies for private account or history data.
4. Consider upload limits, response status codes, rate limits, and database transactions.
5. Add a focused backend test.
6. Update this document if the documented API behavior changes.

Changing the user interface

1. Find the component that owns the relevant area: DataEntryForm for schedule inputs, Dashboard for generated schedules, or App for navigation and API workflow.
2. Use React state for values that need to change and render again.
3. Keep API calls and shared account state coordinated through App.
4. Test the feature in the browser using EXAMSCHEDULER.bat.
5. Run npm run build from the frontend directory to catch compilation errors.
6. Run npm run lint from the frontend directory if lint validation is needed.

Changing database fields

1. Update the SQLAlchemy model and all code that reads or writes the field.
2. Decide how existing SQLite and PostgreSQL databases will acquire the new field. create_all creates missing tables but does not automatically migrate every changed column.
3. Add a migration or explicit compatibility logic for existing databases.
4. Add tests against a temporary SQLite database.
5. Back up any real database before applying a schema change.

Changing exports

The server exporter is backend/app/exporter.py. The browser fallback is frontend/src/utils/docxExporter.js. Update both when a change should appear in either implementation. Add a regression test for the server output and manually test the browser fallback where possible.

33. Troubleshooting guide

The launcher says Python was not found

Install Python 3. Reopen the project folder and try again. If Python is installed but the message persists, add Python to PATH or configure the installation so the python command is available.

The launcher says Node.js or npm was not found

Install Node.js, which includes npm. Reopen the terminal or restart Windows so PATH updates are visible. Run the launcher again.

pip fails while installing

Check internet access, Python version compatibility, disk space, and the error text in the backend window. Confirm backend/requirements.txt can be read. A corporate proxy or firewall may block the package index.

npm ci fails

Check internet access and Node.js version. Confirm frontend/package-lock.json and frontend/package.json exist. Keep the error window open so the package name and failure reason can be read.

Browser says localhost refused the connection

Check that both command windows remain open. Look for an import error or a port-in-use message. The API should respond at http://localhost:8000/health and Vite should respond at http://localhost:5173. If startup is still in progress, wait and refresh once.

Port 5173 or 8000 is already in use

Close the other application using that port, or stop its process using its own supported controls. Do not randomly terminate unrelated processes. The frontend port is configured in frontend/vite.config.js; the API port appears in EXAMSCHEDULER.bat.

Sign-in says the credentials are wrong

Confirm the exact username and password. Usernames are normalized to lowercase. There is no password-reset feature. Creating a different username creates a separate history workspace and will not recover the previous one.

Sign-in returns to the login screen or the account page does not load

Keep the backend and frontend command windows open, then restart EXAMSCHEDULER.bat to ensure both services are running the current project version. The browser needs access to the API, and backend CORS must allow the frontend origin and the Authorization header. The frontend keeps the signed access token in localStorage; the backend keeps the password hash and account in data/exam_duty.db. Check the backend window for startup or database errors. After a successful sign-in, choose Create a duty schedule on the home screen to open the scheduling form.

A schedule does not use expected historical totals

Confirm the exam was marked complete, confirm the correct username is signed in, and check that teacher names match exactly. An imported history workbook adds totals to existing values; it does not replace them.

An Excel list is rejected

The list importer accepts .xlsx and .xlsm, reads the first worksheet, and has a 10 MB size limit. Check that the workbook is valid and that the teacher or room name column is selected.

An Excel history workbook is rejected

The first worksheet must include a recognized teacher-name heading and total-duty heading. Duty totals must be whole non-negative numbers. The same exact workbook file cannot be imported twice into the same workspace.

The app looks different without internet access

The app's core local functions do not require a hosted service. The Google Fonts DM Sans asset may not load, in which case the page uses a fallback sans-serif font. First-time package setup still needs downloads unless dependencies are already cached.

History seems to have disappeared

The local SQLite data is stored in data/exam_duty.db. Check whether the project folder changed, whether the database file was deleted, whether a different copy of the repository is being run, or whether a different username is signed in. Restore a backup if the database was removed.

34. Additional interview review

Question: Why separate the frontend and backend during development?

Answer: The frontend focuses on interaction and presentation while the backend owns validation, scheduling, authentication, and persistence. The API boundary lets each side evolve independently, but it requires correct URLs and CORS configuration during local development.

Question: What is the difference between a development server and a production server?

Answer: A development server provides convenient source reloads and debugging. This project uses Vite and Uvicorn reload for local development. A production server uses built assets and stable process configuration without development reload behavior. Docker builds static frontend assets and uses a backend server process, but a production public deployment still requires additional hosting and security configuration.

Question: What is a virtual environment?

Answer: A virtual environment is an isolated Python package directory associated with a Python interpreter. Here it is backend/venv. It prevents this application's Python packages from being mixed with global packages or packages used by unrelated projects.

Question: What is the difference between npm install and npm ci?

Answer: npm ci installs exactly the dependency resolution recorded in package-lock.json and is suited to repeatable setup. npm install can update the lock file when package declarations change. The launcher uses npm ci.

Question: What is the difference between an image, a container, and a volume?

Answer: An image is a built package of application files and runtime dependencies. A container is a running instance of an image. A volume is separate persistent storage that can survive replacement of a container. In this project, the PostgreSQL container stores its database in a named volume.

Question: Why can containers talk to the database using db?

Answer: Docker Compose creates a private network and registers each service name in its internal name resolution. The app container can use the db service name. A process running directly on Windows generally cannot resolve that name.

Question: What is a health check?

Answer: A health check periodically tests whether a service is responsive. The Compose file checks PostgreSQL readiness and the app's /health endpoint. It helps startup ordering and monitoring but does not replace functional tests.

Question: What is CORS preflight?

Answer: Before certain cross-origin requests, a browser sends an OPTIONS request asking whether the API permits the origin, method, and headers. The backend CORS middleware answers according to CORS_ORIGINS and configured methods and headers.

Question: What are status codes 401, 409, and 422 used for here?

Answer: 401 means authentication is missing or invalid. 409 means a conflicting record exists, such as a duplicate username or exam history entry. 422 means request fields fail validation rules.

Question: Why are names not primary keys for teachers?

Answer: The current system uses teacher-name strings for input and history matching because it is simple for spreadsheet workflows. This means spelling changes can split a person's history. Stable teacher IDs would be a more robust design for a larger deployment.

Question: Why is the duty algorithm called greedy?

Answer: It picks the best available teacher for the current room based on the current totals, then proceeds to the next room. It does not revisit previous choices or evaluate every full schedule combination.

Question: Why is SystemRandom used for ties?

Answer: SystemRandom draws randomness from the operating system rather than using a repeatable seeded pseudo-random sequence. This avoids deterministic tie ordering in ordinary use. It also means tests should assert fairness invariants, not one exact schedule.

Question: What is idempotency and how does history import approach it?

Answer: An idempotent operation can be repeated without applying the same effect twice. The history import stores a hash of workbook bytes and rejects an exact repeat. A workbook with different bytes but equivalent rows is not considered identical by this hash check.

Question: What is a database transaction?

Answer: A transaction groups database changes so they can be committed together or rolled back on failure. Account registration and history operations use SQLAlchemy sessions and commits. A failure during multi-row history writes should be considered carefully to avoid partial updates.

Question: Why are Python type annotations useful here?

Answer: They document the intended values, help editor analysis, clarify function contracts, and support Pydantic and SQLAlchemy typed models. They do not by themselves validate every ordinary Python value at runtime.

Question: What is the difference between authentication and authorization?

Answer: Authentication checks who is making the request. Authorization checks whether that user may perform the requested operation. The app authenticates private endpoints using JWTs and scopes history queries by the authenticated user's school_id. The current role field is stored but role-based permission checks are not a major part of the current workflow.

Question: What data should never be committed to Git?

Answer: Real passwords, APP_SECRET_KEY values, database connection strings, .env files, local database contents, and private exports should not be committed. .gitignore excludes common local data files, but developers should still inspect git status and staged changes before committing.

Question: If more users needed to access the app from different computers, what would have to change?

Answer: The deployment would need a host reachable by those computers, a persistent shared database, TLS, a production-grade secret, backups, persistent rate-limit storage, access controls, and security review. The current local launcher is not that deployment.

35. Short technical summary for interviews

The project is a React and FastAPI full-stack scheduling application. React with Vite presents the schedule form and room-based chart. FastAPI validates JSON using Pydantic and exposes account, allocation, history, upload, and export endpoints. SQLAlchemy persists users and duty history in SQLite locally and PostgreSQL in Docker Compose. The allocation algorithm greedily chooses the available teacher with the lowest saved plus current duty total and randomly breaks equal-total ties. CSV is parsed in the browser; Excel is processed using openpyxl. DOCX files are generated with python-docx on the server and with the JavaScript docx package as a fallback. A Windows batch script automates local startup, while Docker and YAML configuration are optional container-based self-hosting tools.
