EXAM DUTY ALLOCATOR
Project and System Design Document

Purpose

This document describes the system as implemented in this repository. It is a concise reference for users, maintainers, demonstrations, and technical interviews. Implemented behavior is stated as fact; future improvements are identified as recommendations. The application is local-first and is not a public hosted service.

1. Project summary

Exam Duty Allocator creates room-by-room invigilation schedules for examination sessions. It uses saved teacher duty totals to favor teachers with fewer previous and current duties, prevents assigning a teacher to multiple rooms in the same session, and lists unused teachers as standby staff.

Users can review and adjust assignments, export a Word duty chart, and explicitly record completed exams in account history. CSV/Excel input and Excel history import/export are supported. Generated schedules do not affect future history until the user marks an exam complete.

Primary objectives:
- Reduce manual work preparing exam duty charts.
- Distribute repeated duties using transparent historical totals.
- Keep each account's history separate.
- Support a simple local Windows workflow, with Docker Compose as an optional private self-hosting route.

2. Architecture and system design

Logical flow

  Browser (React UI)
       | HTTP JSON, multipart uploads, Bearer access token
       v
  FastAPI application
       |-- Pydantic validation and API routes
       |-- Allocation algorithm and export/import operations
       |-- Authentication and account-scoped history
       v
  SQLAlchemy database layer ---> SQLite (local) or PostgreSQL (Docker Compose)

Development serves the frontend through Vite at http://localhost:5173 and the API through Uvicorn at http://localhost:8000. The browser calls the API over HTTP. In the Docker image, Vite builds static frontend files and FastAPI serves those files and the API from the same application origin on port 8000.

Request lifecycle for schedule generation:
1. The React form collects the exam, sessions, teachers, and rooms.
2. The frontend sends JSON to POST /allocate with the signed-in user's Bearer token.
3. FastAPI validates the request with Pydantic and resolves the account from the token.
4. The route loads duty totals for that account's workspace. It replaces any history totals supplied by the browser with database values.
5. The allocator selects teachers and returns schedule, duty counts, and standby names.
6. The frontend renders the result. Edits remain in browser state until export or explicit completion.

Data persistence boundaries:
- SQLite or PostgreSQL stores users, password hashes, cumulative duty totals, completed-exam logs, per-exam duty contributions, and imported-workbook hashes.
- The browser keeps the access token in localStorage and holds the current unsaved schedule in application state.
- CSV parsing is done in the browser. Excel parsing and history operations are performed by the backend.
- DOCX export is primarily server-side; the frontend has a fallback exporter if the API export fails.

4. Scheduling behavior

Inputs are school name, exam name, one or more sessions, teacher names, room names, and historical totals. Session date and time slot are strings; the backend does not currently validate calendar dates, time zones, or overlaps.

Allocation algorithm:
1. Trim teacher and room names, remove blank values, and de-duplicate exact strings while preserving order.
2. Reject missing teachers, rooms, or sessions. Reject any session with more rooms than teachers.
3. For each session, make every teacher available. For each room, choose an available teacher with the lowest historical total plus duties already assigned in this request.
4. Select randomly among equal minimum totals using Python's SystemRandom. Remove each selected teacher from availability for that session, then increment their current duty count.
5. Return the assignments, duty counts, total shifts, and teachers who were never assigned as standby.

A teacher can work in different sessions but at most once in each session. The algorithm is a greedy heuristic, not a global optimizer. It does not model availability, preferences, qualifications, room constraints, maximum workload, or weighted duties. Name matching is exact, so inconsistent spelling/capitalization splits a teacher's history.

Manual changes are checked by the frontend. It computes cumulative totals (saved history plus current schedule) and permits a swap or standby substitution only if the highest-minus-lowest total does not increase. This is a guardrail, not a proof of global optimality.

5. Data model and history

Each registration creates a user and a separate School workspace. Current history is scoped by school_id, so one account does not read or change another account's totals. To share a workspace, users must share the same login; there is no multi-user invitation flow.

Database records:
- School: account history workspace.
- User: normalized unique username, school link, password hash, and role. Legacy email and verified columns remain for compatibility; new accounts do not use email.
- DutyHistory: cumulative total per teacher within a workspace.
- CompletedExam: exam name, identifier, and completion time; workspace plus exam identifier is unique.
- ExamDuty: per-exam teacher contributions used for the exam log.
- DutyImport: SHA-256 hash preventing the same exact workbook bytes from being imported twice into one workspace.

History rules:
- Completing an exam adds its counts to cumulative totals and records the per-exam log. Duplicate exam identifiers in the same workspace are rejected.
- History workbook imports add totals; they do not replace or reconcile existing totals.
- History export contains Teacher Totals and Exam Log sheets.
- Exact teacher names are the history key. Stable naming is important.
- SQLite is created at data/exam_duty.db when DATABASE_URL is unset. Docker Compose uses PostgreSQL and a persistent named volume.

6. Authentication

Registration accepts usernames of 3-32 letters, digits, dots, underscores, or hyphens. Usernames are trimmed and converted to lowercase. Passwords must be 12-256 characters. A password is hashed using pwdlib's recommended configuration, which supports Argon2; plaintext passwords are not stored.

On successful registration or login, the API issues a signed JWT:
- Algorithm: HS256.
- Claims include user ID (sub), token purpose, issued-at time, and expiration.
- Access-token lifetime: 12 hours.
- Protected requests send Authorization: Bearer <token>.
- The backend verifies signature, expiry, purpose, and that the user still exists.
- The frontend stores the access token in localStorage and removes it when invalid or when the user signs out. There is no server-side token revocation or refresh-token flow.

There is no email verification, password reset, account recovery, or account transfer. New registration creates an isolated workspace and cannot recover an old account's history.

7. API and file formats

Health and docs:
- GET /health: unauthenticated process health response.
- GET /docs: FastAPI interactive API documentation during local operation.
- GET /: serves the built frontend when available; otherwise returns API status information.

Authentication and history:
- POST /auth/register: create account; limited to 5 requests per IP per hour.
- POST /auth/login: verify credentials; limited to 10 requests per IP per minute.
- GET /auth/me: return current account details; authenticated.
- GET /auth/history: return current cumulative totals; authenticated.
- POST /auth/history/record: record a completed exam; authenticated.
- POST /auth/history/import: add totals from an XLSX/XLSM workbook; authenticated; limited to 5 requests per IP per hour.
- GET /auth/history/export.xlsx: download totals and exam log; authenticated.

Scheduling and files:
- POST /allocate: generate a schedule from account history; authenticated.
- POST /import-list: read non-empty rows from the active worksheet of an XLSX/XLSM file; no authentication is currently required.
- POST /export: generate a DOCX from the submitted schedule; no authentication is currently required.

File handling:
- CSV lists are parsed in the browser. Excel lists accept .xlsx/.xlsm and the backend reads the active worksheet.
- List and history workbook uploads are limited to 10 MB. History workbooks need a recognized teacher-name column (Teacher, Teacher Name, Staff, Staff Name) and a duty-count column (Total Duties, Duties, Duty Count, Total Shifts). Counts must be non-negative integers.
- DOCX output contains session/room assignments and standby lists, not a fairness matrix. Client and server exporters are separate implementations and should be kept consistent.

8. Security and privacy

Implemented controls:
- Passwords are stored as password hashes, not plaintext.
- Protected account, history, and allocation routes require a signed, expiring Bearer token.
- The backend scopes history queries to the authenticated user's workspace.
- Registration, login, and history import have IP-based rate limits.
- CORS allows configured browser origins and specific methods/headers. CORS is a browser policy, not API authentication.
- Excel uploads have an extension allowlist and 10 MB limit; history imports validate columns and values.
- APP_ENV=production rejects the known development signing key and requires PostgreSQL.

Security boundaries and risks:
- The local launcher binds Vite and Uvicorn to 127.0.0.1. The Docker container binds to 0.0.0.0 and Compose publishes a host port; remote exposure depends on host/network configuration.
- The project does not configure TLS, a reverse proxy, encrypted database storage, automated backups, or production security headers. Do not expose it publicly without adding and reviewing these controls.
- localStorage is accessible to JavaScript running in the page, so a successful cross-site scripting flaw could expose the token. Use HTTPS for remote access and assess a secure cookie or other token-storage strategy before public deployment.
- The API's list-import and DOCX-export routes are currently unauthenticated. CORS does not prevent non-browser clients from calling them.
- The default development JWT key is only for local use. Production requires a unique secret kept outside source control.
- Rate limits use in-memory storage by default; limits are not shared across app processes. Use a shared store such as Redis for multiple replicas.
- The application does not automatically back up the SQLite file or PostgreSQL volume. Teacher names and duty records may be sensitive operational data; restrict access and back up securely.

9. Run and deployment

Windows local development:
1. Install Python 3 and Node.js/npm and make them available on PATH.
2. Run EXAMSCHEDULER.bat from the repository. It creates backend/venv if needed, installs backend requirements, runs npm ci if frontend dependencies are missing, starts Uvicorn and Vite in separate windows, then opens http://localhost:5173.
3. Keep both service windows open. Closing them stops the application.
4. Local SQLite history is stored in data/exam_duty.db. Back it up before moving or removing the project.

Docker Compose private self-hosting:
1. Create a .env file with unique APP_SECRET_KEY and POSTGRES_PASSWORD values. APP_PORT and RATE_LIMIT_STORAGE_URI are optional.
2. Run docker compose up --build, then open http://localhost:8000.
3. Compose builds the frontend, runs the API in production mode, starts PostgreSQL, and persists PostgreSQL data in the exam-duty-data volume.

Configuration:
- DATABASE_URL: optional database URL; default is local SQLite, Docker sets PostgreSQL.
- APP_SECRET_KEY: JWT signing secret; use a unique secret in deployment.
- APP_ENV: setting production activates production startup checks.
- CORS_ORIGINS: comma-separated allowed browser origins; defaults to local Vite origins.
- RATE_LIMIT_STORAGE_URI: SlowAPI storage; defaults to in-memory.
- VITE_API_URL: optional API base URL compiled into the frontend; development defaults to localhost:8000 and production defaults to same-origin.

The Windows launcher is for local development, not a Windows service or hardened production install. Docker is an alternative self-hosting setup, not a public cloud deployment. For access beyond the local machine, configure TLS, network restrictions, backups, monitoring, and shared rate-limit storage.

10. Testing and CI/CD

The repository has backend unittest coverage for allocation, account/history behavior, spreadsheet handling, migration, and DOCX output. Run from the backend directory:

  python -m unittest discover -s tests

Frontend package scripts:
- npm run lint: ESLint checks JavaScript/JSX.
- npm run build: Vite production build.

There is no configured CI/CD pipeline or GitHub Actions workflow in this repository. These commands are currently run manually. Docker builds the frontend and installs the backend, but its Dockerfile does not run the test suite. No dedicated frontend automated test suite is currently configured.

Recommended future CI pipeline (not currently implemented): install dependencies; run backend unit tests; run frontend lint and build; build the Docker image; publish/deploy only after tests pass and deployment secrets are configured. Production deployment should be a controlled, reviewed step rather than embedding secrets in the image or repository.

11. Limitations and next improvements

Current limitations:
- Greedy fairness is not a full constraint solver; teacher availability, qualifications, preferences, and maximum workloads are not modeled.
- Dates and times are strings without calendar, time-zone, or overlap validation.
- Exact name matching can split totals when spelling or capitalization changes.
- There is no recovery flow, multi-user workspace invitation, token revocation, or automatic backup.
- In-memory rate limits are suitable for one process, not coordinated replicas.
- Python requirements specify minimum versions, not a fully locked environment; the frontend does have package-lock.json and uses npm ci.
- There is no frontend automated test suite or CI/CD workflow.

Practical improvements, if required: canonical teacher IDs and merge tools; date/time validation; availability and qualification constraints; frontend integration tests; Python dependency locking; backup/restore procedures; shared rate-limit storage; and deployment hardening. A constraint solver is appropriate only if real scheduling rules outgrow the current heuristic.

12. Interview and review questions

Q: What problem does this application solve?
A: It automates room-level exam invigilation assignments, exposes standby staff, and uses historical totals to distribute repeated duties more evenly.

Q: Explain the architecture.
A: React/Vite is the browser client; FastAPI validates and serves API requests; the allocator implements scheduling; SQLAlchemy persists accounts and history in SQLite locally or PostgreSQL in Docker. The browser communicates with the API over HTTP.

Q: How does a schedule request work?
A: The frontend submits sessions, teachers, and rooms to POST /allocate with a Bearer token. The backend resolves the user, loads that workspace's history, runs the allocator, and returns a validated response for the dashboard.

Q: How is fairness implemented?
A: For each room, choose an available teacher minimizing historical duties plus duties assigned earlier in the current generation. Randomize equal-total ties. A selected teacher is unavailable for the rest of that session.

Q: Is the generated schedule globally optimal?
A: No. It is a greedy heuristic that balances duty counts locally. It does not consider availability, qualifications, preferences, or other complex constraints.

Q: How do manual edits protect balance?
A: The frontend compares the cumulative highest-to-lowest duty spread before and after a proposed swap or standby replacement and rejects changes that increase that spread.

Q: Why save history only after completion?
A: A generated schedule may be a draft. Explicit completion prevents unused plans from incorrectly affecting future allocations.

Q: How does authentication work?
A: The API hashes passwords, returns a signed HS256 JWT after registration/login, and requires the token in a Bearer header for protected routes. Tokens expire after 12 hours; the frontend stores them in localStorage.

Q: What is the main authentication trade-off?
A: Stateless JWT verification avoids a server-side session lookup, but tokens are not revocable before expiry and localStorage is exposed to page JavaScript. There is no refresh or account recovery flow.

Q: How are records isolated?
A: Each registration creates a workspace. History reads and writes filter by that workspace ID. Sharing requires sharing one account's credentials; there is no invitation or role-management workflow.

Q: Why SQLite and PostgreSQL?
A: SQLite makes local setup self-contained. PostgreSQL is used by Docker Compose for a separate persistent database service and is required by the production startup guard.

Q: How are spreadsheet re-imports handled?
A: The history importer validates the first worksheet and adds non-negative integer totals. A SHA-256 hash per workspace rejects an identical workbook upload; importing a changed workbook can add totals again.

Q: What does CI/CD mean here, and what is implemented?
A: CI runs automated integration checks on changes; CD automates delivery/deployment. This repository has no configured pipeline. Backend tests, frontend lint/build, and Docker build are available commands, but are not automatically run by a CI service.

Q: What are the key security controls and gaps?
A: Password hashing, expiring signed tokens, route-level authentication, account-scoped history, upload limits, and selected rate limits are implemented. TLS, backups, encrypted storage, shared rate-limit storage, and public-deployment hardening are not configured. CORS is not an authentication control.

Q: What would you improve next?
A: Add frontend tests and CI, formal date/time and scheduling constraints, canonical teacher IDs, recovery and collaboration if needed, and documented secure backup/deployment procedures.

13. Demonstration checklist

- Start the app and create an account.
- Generate a schedule with at least as many teachers as rooms.
- Show unique assignments per session, saved-history balancing, and standby names.
- Demonstrate an allowed edit and an edit rejected for worsening the duty spread.
- Export a DOCX, mark the exam complete, and verify the updated history.
- Export history to Excel and explain that local data resides in data/exam_duty.db.
- State clearly that no CI/CD workflow or public hosted deployment is configured.

Quick glossary

API: HTTP routes used by the frontend to request backend operations.
Bearer token: an access token sent in the Authorization HTTP header.
CORS: browser policy controlling which web origins may read API responses; it is not access control for the API itself.
CI/CD: automated integration checks and delivery/deployment workflows.
Greedy heuristic: an algorithm that makes the best available local choice at each step rather than searching all complete solutions.
ORM: a library, SQLAlchemy here, that maps Python objects to relational database records.
Workspace: the account-scoped School record that owns teacher totals and exam history.
